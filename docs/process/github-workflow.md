# GitHub Workflow

Этот документ задаёт правила, по которым FocusGlass ведётся в GitHub. Он нужен не для формальности: проект растёт, и без дисциплины веток, коммитов, тегов и релизов будет трудно откатываться, проверять изменения и продолжать работу после пауз.

## Ветки

### Solo-схема

Проект ведётся одним владельцем, поэтому заранее не плодим много параллельных
веток. Базовая схема:

- `main` - стабильная ветка. В неё попадает только код, который собран и проверен.
- `feature/next` - основная рабочая ветка для новых возможностей, roadmap-задач,
  UI-полировки и связанных тестов/документации.

### Имена веток

`feature/next` используется по умолчанию для нововведений. Дополнительную ветку
создаём только когда это явно удобнее: срочный фикс, отдельная документационная
правка, релизная подготовка или эксперимент, который не должен мешать текущей
работе.

Для коротких отдельных веток используем английский префикс и понятную суть через
дефис:

```text
feature/next
fix/strict-warn-return
chore/github-workflow
docs/readme
refactor/timer-presets
test/strict-actions
```

Правило: не создавать ветки "про запас". Если несколько изменений идут как один
roadmap-шаг и проверяются вместе, они могут жить в `feature/next`. Если задача
изолированная и должна merge-иться отдельно, тогда создаётся короткая отдельная
ветка.

## Коммиты

Коммиты пишутся на русском. Формат:

```text
тип: краткое действие
```

Разрешённые типы:

- `фича` - новая пользовательская возможность;
- `фикс` - исправление бага;
- `доки` - документация;
- `тесты` - тесты;
- `рефактор` - переработка без изменения поведения;
- `стиль` - визуальная/UI-полировка без изменения логики;
- `сборка` - SwiftPM, package, scripts, CI;
- `инфра` - GitHub, шаблоны, workflow, housekeeping;
- `архив` - перенос неиспользуемого в `archive/`;
- `релиз` - подготовка версии.

Примеры:

```text
фича: добавить кастомные таймеры
фикс: вернуть пользователя к fullscreen при strict warn
доки: описать правила веток и релизов
тесты: покрыть pauseSession в strict mode
архив: вынести неиспользуемые модели persistence
```

Тело коммита добавляется, если нужно объяснить причину или риск:

```text
фикс: не терять workspace при битом settings.json

settings.json теперь восстанавливается отдельно от workspace.json.
Это сохраняет проекты и задачи даже при ошибке декодирования настроек.
```

Если коммит делает ассистент, в теле коммита обязательно добавляется подпись:

```text
Ассистент: Codex
```

Так владелец проекта сразу видит, какие коммиты были сделаны вручную, а какие
сделал ассистент.

## Pull Request

Даже если разработка идёт локально, PR-шаблон задаёт качество проверки. Название
и описание PR пишутся на русском.

Если PR создаёт ассистент, в описании PR должна быть строка:

```text
Ассистент: Codex
```

Перед merge в `main` должно быть понятно:

- что изменилось;
- почему это нужно;
- какие файлы затронуты;
- как проверено;
- обновлены ли docs/handoff;
- есть ли риск для пользовательских данных, permissions или сборки.

## Теги и релизы

Теги:

```text
v0.1.0
v0.1.1
v0.2.0
v1.0.0
```

Версионирование:

- `PATCH` - исправления без новых больших возможностей;
- `MINOR` - новые функции без ломки данных;
- `MAJOR` - существенные изменения поведения, данных или совместимости.

Команда для тега:

```sh
git tag -a v0.1.0 -m "релиз: v0.1.0"
git push Release v0.1.0
```

Release notes пишутся на русском и берутся из `CHANGELOG.md`.

## Релизные артефакты

`build/` - локальный generated output. Он нужен для ручной QA и подготовки
релизного архива, но не является источником правды и не коммитится в git.

Для локального tester handoff:

```sh
swift build --disable-sandbox
swift test --disable-sandbox --scratch-path /tmp/FocusGlassApp_MacOS-swift-test
./Scripts/package-release.sh
```

`Scripts/package-release.sh` по умолчанию создаёт:

```text
build/releases/<version>/FocusGlass.app
build/releases/<version>/FocusGlass-<version>.zip
build/releases/<version>/FocusGlass-<version>.zip.sha256
```

Zip и checksum не переносятся в tracked files. Пока проект не перешёл на
подписанный/notarized канал распространения, такие архивы считаются локальными
unsigned сборками для ручной проверки и аккуратной передачи тестеру.

GitHub Release можно использовать как ручную страницу раздачи уже собранного
архива. Это не сборка приложения. Процесс:

1. Выбрать конкретный git commit, который считается сборкой.
2. Поставить tag, например `v0.0.2-test.1` для теста или `v0.0.2` для обычной версии.
3. Создать Draft/Pre-release на GitHub, привязанный к этому tag.
4. Прикрепить `FocusGlass-<version>.zip` и соответствующий `.sha256`.
5. Написать release notes на русском и дать тестеру ссылку на Release.

Для первого пробного handoff использовать Draft или Pre-release, чтобы не
создавать давление "официального" релиза.

## Branch Protection

Позже, когда появится стабильный PR/release процесс, для `main` можно включить
в GitHub:

- запрет force push;
- запрет удаления ветки;
- pull request перед merge;
- требование прохождения CI;
- linear history, если GitHub-процесс станет командным;
- администратор может временно обходить правило только для аварийного восстановления.

## CI

Минимальная проверка:

```sh
swift test --disable-sandbox --scratch-path /tmp/FocusGlassApp_MacOS-swift-test
```

Полная локальная проверка перед релизом:

```sh
swift build --disable-sandbox
swift test --disable-sandbox --scratch-path /tmp/FocusGlassApp_MacOS-swift-test
./Scripts/package-app.sh
```

Для permission QA запускать `build/FocusGlass.app`, не `swift run`.

GitHub Actions workflow добавляем только из среды, где push-токен имеет
`workflow` scope. Иначе GitHub отклонит коммит с `.github/workflows/*`, а
репозиторий останется в промежуточном состоянии. До этого CI считается
процессным блокером, а не отсутствующей локальной проверкой. В ближайшем
простом tester handoff branch protection и CI не настраиваются.

## Правила для ассистента

Когда ассистент делает изменения:

1. Перед работой проверяет `handoff.md`, `docs/assistant-context.md` и релевантные файлы.
2. Делает отдельную ветку, если задача не является маленькой правкой.
3. Не коммитит `.build/`, `build/`, `.swiftpm/`, `.Rhistory`, `xcuserdata`.
4. Обновляет docs/handoff при изменении поведения, архитектуры, QA или процесса.
5. Проверяет build/tests по масштабу изменения.
6. Пишет коммит на русском по правилам выше.
7. Добавляет в тело каждого своего коммита подпись `Ассистент: Codex`.
8. Создаёт PR на русском и подписывает описание строкой `Ассистент: Codex`.
9. Пушит изменения в GitHub, если remote доступен.

## Что не делать

- Не смешивать несвязанные изменения в одном коммите.
- Не переписывать историю `main` без прямого решения владельца проекта.
- Не удалять архивы/сгенерированные файлы без проверки release flow.
- Не ставить сторонние skills или actions без чтения их содержимого.
